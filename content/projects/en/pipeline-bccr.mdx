## Problem

The Central Bank of Costa Rica (BCCR) publishes its economic indicators through its SDDE service. This project takes six of them every day, checks them and serves them from one database, as a public API and as a dashboard.

The source has two traits that shape the design. The BCCR can correct a value after it publishes it. And some indicators publish dates ahead of time: the exchange rates one day, the basic passive rate ten days.

## My role

I built it alone, end to end: the ETL, the database, the API, the dashboard, the tests and the automation.

## What I built

An ETL in Python 3.12 runs on GitHub Actions twice a day. It downloads six indicators from the SDDE API of the BCCR: the reference exchange rate (buy and sell), the consumer price index and its year-on-year change, the basic passive rate and the monetary policy rate. It validates every row, saves them in PostgreSQL 17 and compares them with the source afterwards.

A NestJS API serves the data read-only: all the indicators with their last value, one indicator, a series between two dates, and two health routes. It has Swagger and a limit of 60 requests per minute per IP. A Next.js dashboard with Tailwind and Recharts shows the indicators and renders with ISR.

Monitoring runs on GitHub Actions. `/salud` answers 503 after 36 hours without a data load, and Playwright tests run every hour against production, at 375 and 1280 px. They also run locally and after each deploy. The API runs on the free plan of Render and it kept spinning down, because the ping from GitHub Actions was too irregular. A free outside ping from cron-job.org now calls `/salud/vivo` every 5 minutes. That route does not touch the database, so the Neon database can still scale to zero.

## Key decisions

### No ORM

Three read-only tables do not need one. The API uses parameterized SQL with `pg`. I did not use an ORM.

### Gaps are never filled

If the BCCR did not publish a date, that date does not exist in the database. Long gaps are logged as warnings. I did not fill them in.

### BCCR corrections are kept

Each daily run asks again for the last 60 days. If a value changed, the old value is saved in the `revision` table with the new one. A correction does not erase history.

### Minimum privileges in the database

The ETL role can insert and update observations and loads, and it can only add rows to the `revision` table. It cannot delete rows or change the schema. The API role can only read.

## Results

The dashboard and the API are published, and the history starts in 2015.

On 16 November 2026 I checked 18 values, 3 dates for each of the 6 indicators, against sdd.bccr.fi.cr. All 18 matched.

GitHub Actions cron jobs can run late or be skipped, so the load runs twice a day over a window of 60 days, and the hourly check warns when the last scheduled run is older than 18 hours.

## What I'd do next

- Handle a new CPI base without a manual step. Today, if the BCCR publishes another base, I edit `etl/indicadores.yaml` and repeat the backfill of the two CPI series.
- Move the API off the free plan, so it does not need an outside ping to stay awake.
